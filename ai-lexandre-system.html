System Architecture — V2

AI-lexandre

Recruiter-facing interview assistant over my portfolio evidence.

AI-lexandre is a production-style RAG system: a static GitHub Pages frontend, a Railway-hosted Fastify API, a generated local evidence corpus, and a structured routing layer that classifies interview intent before retrieval. V2 replaced V1’s ad-hoc intent branches with an explicit planner, retrieval policy, structured memory, and answer policy so each response uses the right source types and chips reflect the actual answer.

Architecture

The system separates the static portfolio from the interview runtime. V2 adds a routing layer between the request and retrieval so intent drives source-type selection before any evidence is scored.

Static Client

GitHub Pages

interview/index.html, app.js, and config.js render the chat UI, role presets, streaming tokens, sources, follow-up chips, and now persist the structured MemoryState between turns.

API

Fastify on Railway

apps/interview-api exposes health, config, evidence search, full response, and streaming response endpoints. V2 adds memoryState to both the request and response schemas.

Routing (V2)

Intent Planner + Policy

intent-planner.ts classifies the question into a typed intent, extracts named entities, and derives source-type filters before any retrieval runs. retrieval-policy.ts converts the plan into evidence ordering rules and answer-policy.ts injects focused per-turn instructions into the model prompt.

Evidence

Generated Corpus

content.json is converted into chunks from projects, case studies, internships, education, and skills. V2 applies source-type pre-filtering so school questions only score education chunks and experience questions only score experience chunks.

Model

OpenAI Responses

The API sends the selected evidence blocks, role preset, question, history, and a short per-turn answer guidance block derived from the plan intent.

V2 Request Flow

  1. The client sends the question, history, and the MemoryState from the previous turn.
  2. planInterviewTurn() classifies intent, extracts entity names, and derives source-type filters and a targeted retrieval query.
  3. buildRetrievalPolicy(plan) converts the plan into retrieval options (topK, maxPerSource, sourceTypes) and a refine() function for post-scoring ordering.
  4. retrieveEvidence() scores only the candidate chunks allowed by sourceTypes. policy.refine() applies section ordering, entity boosting, and freshness filtering.
  5. The answer is generated with focused per-intent instructions appended to the user prompt. chipSourceTypeFilter() hard-gates which source types can appear as citations.
  6. The response includes the answer, citations, follow-ups, retrieval trace, and a new MemoryState for the client to persist.

Evidence Flow

  1. content.json is the source of truth for all public portfolio evidence.
  2. packages/interview-core builds a corpus with source type, title, section, citation label, URL, keywords, and role tags.
  3. The intent planner emits a sourceTypes allowlist. Chunks outside it are excluded before scoring, so they cannot compete for topK slots at all.
  4. After scoring, the retrieval policy’s refine() step handles section preferences (coursework vs base education records), entity boosting (CHANEL first for CHANEL questions), and source freshness (exclude recently cited sources when “other/different” is asked).
  5. Chip display is filtered twice: once by answer-text reference matching, then by the answer policy type allowlist. Education-schools answers cannot show project chips even if retrieval returned them.

V1 vs V2

V1 accumulated intent detection as inline functions that could not see each other’s outputs. This caused predictable routing failures. V2 replaces those branches with an explicit planner that runs once per turn.

Routing Layer Design

The V2 routing layer is three modules in sequence. Each module is pure, independently testable, and has no I/O.

Intent Planner

  • Classifies the question into one of twelve typed intents: education-schools, education-coursework, experience-list, experience-specific, project-list, project-specific, role-fit, technical-depth, behavioral, follow-up, inventory, general.
  • Extracts named entities (Columbia, CentraleSupelec, CHANEL, SIGMA, CUIMC, Nantes) from the question. School entities trigger education routing; experience entities trigger experience routing.
  • Derives sourceTypes, excludeSources, recentSourceTitles, topic, retrievalQuery, and answerPolicy from a single pass over the question, history, and memory state.
  • Uses question-only entities for routing to prevent history contamination. History entities augment the retrieval query but do not override the current question’s intent.

Retrieval Policy

  • Translates the plan into concrete retrieval options: topK, maxPerSource, and the sourceTypes pre-filter. List intents (experience-list, project-list) use topK 10 with maxPerSource 1 for diversity; inventory uses topK 14; role-fit uses topK 16.
  • Applies post-scoring refinement: refineEducationSchools puts base school records before coursework; refineEducationCoursework puts coursework first, CentraleSupelec coursework first when that entity is present; refineExperienceSpecific moves named-entity chunks to the front; refineRoleFit orders experience before projects before education.
  • Healthcare questions override the sourceTypes restriction so evidence split across experience and case-study source types can compete together.
  • Optimization follow-ups use refineOptimizationTechnical to exclude the most-recently-cited source and surface fresh project evidence.

Answer Policy

  • buildAnswerPolicyGuidance(plan) produces a focused constraint block injected into the OpenAI user prompt each turn. Education-schools answers are told to stay on school names and dates; experience-specific answers are told to lead with the named entity and include the date range; role-fit answers are told to lead with work evidence before coursework.
  • chipSourceTypeFilter(plan) returns the allowed source types for citation chips based on the answer policy. Education-schools and education-coursework answers cannot show project or case-study chips. Experience answers cannot show education chips unless the answer explicitly cites them.
  • Returns an empty string for intents where the static system prompt is sufficient (general, technical-depth, behavioral), so the prompt stays compact on most turns.

Structured Memory

  • Every response returns a typed MemoryState: activeTopic, recentSources, askedEntities, and lastIntent. Clients persist it and send it back on the next request.
  • The planner uses memoryState.activeTopic directly for follow-up intent resolution instead of parsing it from the compact memory string. recentSources replaces the string-parsed source title list.
  • The old plain-string conversationSummary field is still accepted for backward compatibility. When only that is present, the planner falls back to keyword parsing.

Runtime Contracts

The behavior is encoded as contracts between the client, routing layer, retrieval package, and deployment environment.

Frontend

  • Reads the deployed API base URL from interview/config.js.
  • Maintains local chat state and selected role.
  • Parses NDJSON stream events: meta, token, done, and error.
  • Persists the memoryState from each response and sends it back on the next request for accurate follow-up topic tracking.

API

  • Uses Zod schemas to validate requests, including the optional structured memoryState field.
  • Runs the intent planner, retrieval policy, retrieval, and answer policy in sequence before generation.
  • Streams through the OpenAI Responses API when available.
  • Falls back to deterministic grounded answers if provider generation fails before tokens are emitted.

Retrieval

  • Applies a source-type pre-filter from the planner before any chunk is scored, preventing out-of-category evidence from competing.
  • Lexical scoring applies intent-specific boosts: direct education matches, healthcare domain matches, experience intent signals, and role keyword overlap.
  • Post-scoring refinement handles section ordering, entity boosting, freshness, and assistant-mention exclusion.
  • Diversifies results for list, inventory, and healthcare-domain questions through maxPerSource 1 and larger topK.

Deployment

  • GitHub Pages serves the portfolio and interview client.
  • Railway runs the Fastify API with OPENAI_API_KEY, OPENAI_MODEL, and CORS_ORIGIN.
  • MOCK_INTERVIEW_RESPONSES supports local deterministic mode used by the test suite.
  • The generated corpus is refreshed during the build path when content.json changes.

Architecture Judgment

V1’s risk was behavioral routing rather than infrastructure. V2 addressed that by making routing explicit and testable rather than by adding retrieval infrastructure.

What V2 Changed

  • Replaced inline intent functions in interview-service.ts with a single planInterviewTurn() call that produces a typed plan. All downstream code reads the plan.
  • Replaced refineEvidenceForFocus() with buildRetrievalPolicy(), which owns both retrieval options and post-scoring ordering in one module.
  • Removed nine dead functions from the service layer after the policy absorbed their logic.
  • Added 114 passing tests across unit (planner, policy) and integration (full API scenario) levels.

What Did Not Change

  • The deployment shape: static frontend plus a single Railway API is still the right size for this corpus.
  • The retrieval mechanism: lexical scoring with domain boosts is still sufficient for a curated portfolio corpus and is cheap to inspect and debug.
  • content.json as the single source of truth for both the public portfolio pages and the interview evidence corpus.
  • The absence of a vector database. The structured source-type filter solves the routing failures without adding embedding infrastructure.

Current Judgment

  • The system is now correctly sized at both layers: modest infrastructure and a routing layer that is explicit, testable, and easy to extend one intent at a time.
  • The main quality bar is still "does it answer like a natural interview while staying grounded," not "can it answer." The routing layer enforces the grounding constraint so the model can focus on wording.
  • The next meaningful improvement is not more routing rules but more evidence: richer per-experience interviewFacts, explicit date ranges surfaced as separate corpus chunks, and experienceType fields for routing analytics-specific and research-specific questions.

Why This Structure

  • It keeps the public portfolio static and cheap to serve while the API evolves independently.
  • It makes interview answers auditable: every answer starts from structured local evidence and the routing decisions are logged in the retrieval trace.
  • The routing layer solves the source-selection problem without adding infrastructure. There is no vector database, no embedding pipeline, and no managed retrieval service.
  • Each module in the routing layer (planner, policy, memory) is a pure function with its own unit tests, so intent rules can be added or changed without touching the service layer.
